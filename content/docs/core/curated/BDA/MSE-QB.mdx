### Q1. Explain CAP Theorem and compare it with ACID properties.

<Callout title="Important Concept"></Callout>

The **CAP Theorem** states that a distributed data system can only provide two out of three guarantees at the same time: <Highlight>**Consistency (C)**</Highlight>, <Highlight color="blue">**Availability (A)**</Highlight>, and <Highlight>**Partition Tolerance (P)**</Highlight>. Consistency ensures that all nodes see the same data, Availability ensures every request gets a response, and Partition Tolerance ensures the system continues to work even if the network fails.

In a distributed environment, **Partition Tolerance (P)** is usually mandatory, so NoSQL systems must choose between Consistency (CP) or Availability (AP). For example, a banking system might prioritize consistency, while a social media feed might prioritize availability.

In contrast, traditional relational databases follow **ACID properties**, which stand for **Atomicity, Consistency, Isolation, and Durability**. ACID focuses on ensuring that every transaction is reliable and complete, which is ideal for single-node systems or small clusters where strong consistency is paramount.

While ACID guarantees absolute reliability within a transaction, the CAP theorem helps architects understand the inherent trade-offs involved when scaling data across large, distributed networks.

### Q2. Describe characteristics of NOSQL database. List the different types of NoSQL data stores. Explain any two with diagram.

NoSQL databases are characterized by their **flexible schemas**, **horizontal scalability**, and **high-performance** capabilities. They are designed to manage various data types across distributed clusters, providing a resilient foundation for Big Data applications.

**Types of NoSQL Data Stores:**

| Type | Data Model | Examples |
|------|------------|----------|
| **Key-Value Store** | Stores data as unique keys mapped to values. | Redis, AWS DynamoDB |
| **Document Store** | Stores data as hierarchical documents (JSON/BSON). | MongoDB, Couchbase |
| **Column-Family Store** | Stores data in columns instead of rows. | Apache Cassandra, HBase |
| **Graph Store** | Stores data as nodes and edges (relationships). | Neo4j, JanusGraph |

**Two Types Explained:**

1.  <Highlight>**Document Store**</Highlight>: These databases store data in the form of documents, typically using formats like JSON or XML. Each document is self-contained and can have its own unique structure. This makes it very easy to represent complex, nested data without using join operations.

2.  <Highlight color="blue">**Column-Family Store**</Highlight>: Unlike row-oriented databases, these store data in columns. This is highly efficient for analytical queries that only need to read a few columns from a massive dataset. It also allows for efficient data compression and high write speeds.

Thus, by using different data stores, organizations can match their database technology to the specific structure and access patterns of their data.

### Q3. What is NOSQL? What are the business drivers for NoSQL? Discuss any two architectural patterns of NoSQL. / Q2. What are the types of NOSQL business drivers explain any two with example. / What are NoSQL business drivers? Explain.

NoSQL, which stands for <Highlight>**"Not Only SQL"**</Highlight>, is a database system designed to handle large, distributed data without a fixed schema. Unlike traditional databases, NoSQL is optimized for **horizontal scalability**, high availability, and flexible data models.

It emerged to manage **Big Data**, which is often unstructured and generated rapidly. NoSQL stores data across commodity hardware clusters, offering a cost-effective solution for modern applications.

Thus, it complements SQL by delivering high performance for data-intensive workloads.

**Business Drivers for NoSQL:**

Business drivers are the operational requirements that lead organizations to adopt NoSQL. The key types include:

1.  **Elastic Scalability & Cost-Effectiveness**: The ability to handle sudden traffic spikes dynamically using cheap commodity servers, reducing overall hardware costs.
2.  **Schema Agility**: Allowing development teams to iterate faster by modifying data structures on the fly without complex migrations.
3.  <Highlight>**High Velocity Ingestion**</Highlight>: The capability to process massive, rapid data streams in real-time. 
    *   *Example*: A **smart city telemetry system** using Cassandra can ingest continuous data from thousands of traffic sensors instantly, a load where traditional databases would fail.
4.  <Highlight color="blue">**Complex and Hierarchical Data Management**</Highlight>: The ability to store nested or varying records (like JSON) without rigid tables and complex joins.
    *   *Example*: An **e-commerce platform** using MongoDB can store diverse user profiles—some with one address and others with multiple—allowing the data model to evolve easily.

**Architectural Patterns of NoSQL:**

One pattern is <Highlight>**Master-Slave replication**</Highlight>, where a master node handles writes and slave nodes replicate data to serve reads. This provides **read scalability** and keeps data available if a slave fails.

Another is the <Highlight color="blue">**Shared-Nothing architecture**</Highlight>, where every node is independent with its own resources. Data is distributed across nodes, removing bottlenecks and enabling **linear scalability** and high fault tolerance.

### Q4. Explain NoSQL Architectural patterns. / Q9. Explain shared-nothing architecture to analyse big data.

NoSQL systems use various architectural patterns to manage data distribution across clusters to handle Big Data:

1.  <Highlight>**Shared-Nothing Architecture**</Highlight>: Every node (server) in the cluster is entirely self-sufficient, having its own <Highlight>**local CPU, RAM, and Disk storage**</Highlight>. They communicate only via a high-speed network and do not share disk resources.
    *   **Why it helps Big Data**: It allows for **Linear Scalability**—you simply add more cheap servers as data grows. Processing happens locally on each node, eliminating network bottlenecks and preventing single points of failure.
2.  <Highlight color="blue">**Master-Slave (Primary-Replica) Replication**</Highlight>: A master node handles all writes and replicates them to multiple slave nodes. Slave nodes handle read queries. This speeds up read-heavy applications but the master can become a bottleneck.
3.  <Highlight>**Peer-to-Peer (Leaderless) Architecture**</Highlight>: All nodes are equal and can accept both read and write operations, avoiding any single point of failure and ensuring high cluster availability (e.g., Cassandra).

### Q5. Differentiate between master-slave versus peer-to peer architecture.

Master-Slave and Peer-to-Peer are two different approaches to managing data in a cluster. In a <Highlight>**Master-Slave architecture**</Highlight>, there is a clear hierarchy where one node (Master) handles all writes and coordinates the updates to other nodes (Slaves). This simplifies data consistency but can create a write bottleneck at the master node.

In contrast, a <Highlight color="blue">**Peer-to-Peer architecture**</Highlight> treats all nodes as equals. Any node can accept a write or read request, and updates are synchronized across the cluster using gossip protocols. This provides much higher availability and eliminates single points of failure, though it may result in eventual consistency.

| Feature | Master-Slave | Peer-to-Peer |
|---------|--------------|--------------|
| **Write Handling** | Only Master node | Any node |
| **Consistency** | Stronger / Easier to manage | Eventual / Complex |
| **Availability** | Lower (Master is a SPOF) | Very High |
| **Read Scaling** | Easy (via Slaves) | Easy (all nodes) |

Therefore, Master-Slave is often preferred for applications requiring tight control, while Peer-to-Peer is better for global, resilient systems.

### Q6. Describe characteristics of a NoSQL database.

The defining characteristic of a NoSQL database is its <Highlight>**Schema-less or Flexible Data Model**</Highlight>. Unlike relational databases that require a predefined schema, NoSQL systems allow for the storage of data in various formats such as documents, key-pair values, or graphs. This flexibility supports rapid development and handles semi-structured data effectively.

Another core characteristic is **Horizontal Scalability**. NoSQL databases are designed to be distributed across many nodes, allowing them to handle increased load by adding more servers rather than upgrading a single machine. This distributed nature also provides **High Availability and Fault Tolerance**, ensuring the system remains operational even if several nodes fail.

Additionally, NoSQL systems often provide **Tunable Consistency**, allowing developers to choose the level of consistency required for different operations. This is often based on the **CAP Theorem**, where the system prioritizes Availability and Partition Tolerance over immediate Consistency.

Thus, these characteristics make NoSQL databases highly suitable for modern, large-scale applications that require agility, resilience, and performance.

### Q7. Explain four ways that NoSQL system handles big data problems.

The first way NoSQL handles Big Data is <Highlight>**Horizontal Partitioning (Sharding)**</Highlight>, distributing data across multiple servers. This enables parallel processing and easy scaling by adding standard hardware.

The second method uses <Highlight color="blue">**Write-Optimized Storage engines**</Highlight>, batching multiple writes into a single sequential operation. This drastically improves write speeds for high-velocity data.

Thirdly, they use <Highlight>**Eventual Consistency models**</Highlight>, updating replicas asynchronously. This ensures high availability and fast responses, prioritizing uptime over instant synchronization.

Finally, <Highlight color="blue">**Columnar Storage**</Highlight> stores data in columns rather than rows, boosting analytical query speed and providing better data compression to manage huge datasets efficiently.

### Q8. Agility is a Non-SQL business driver Justify.

Agility is considered a primary driver for NoSQL because it enables <Highlight>**Rapid Development and Faster Deployment cycles**</Highlight>. In a traditional SQL environment, changing a data model often requires complex schema migrations and potential application downtime. NoSQL's schema-less nature allows developers to add new fields and features instantly.

Furthermore, NoSQL supports **Iterative Development**, where teams can refine their data structures based on real-world usage without being locked into a rigid initial design. This aligns perfectly with Agile and DevOps methodologies, allowing for continuous integration and delivery.

Additionally, NoSQL systems provide **Elastic Scalability**, allowing businesses to respond quickly to changing market demands by scaling their infrastructure up or down without re-architecting the database layer.

Hence, NoSQL provides the structural and operational flexibility that modern businesses need to remain competitive in a fast-paced digital economy.
